# Keys and recovery

Everything the SDK signs with comes from one 32-byte master seed. Nothing is random and no secret is stored, so the keys of every channel come back from the user's mnemonic. The signing state does not, and that difference matters.

## The master seed

The SDK never sees the mnemonic. Your wallet turns the mnemonic into its usual 64-byte BIP39 seed, and [`deriveMasterSeed`](/docs/api/functions/deriveMasterSeed) turns that into the master seed you pass to the constructor:

```ts title="seed.ts"
import { FiberLspSdk, deriveMasterSeed, deriveTenantId } from "@peersyst/fiber-lsp-sdk";

// The 64-byte BIP39 seed your wallet already derives from the mnemonic.
const masterSeed = deriveMasterSeed(bip39Seed); // m/1017'/309'/0'
const secondAccount = deriveMasterSeed(bip39Seed, 1); // m/1017'/309'/1'

const tenantId = deriveTenantId(masterSeed); // public, safe to log or key storage by

const sdk = new FiberLspSdk(masterSeed, { network: "testnet", storage, rpcUrl: "https://lsp.example.com/rpc", lspPubkey });
console.log(sdk.tenantId === tenantId, secondAccount.length); // true 32
```

The master seed is the BIP32 private key at `m/1017'/309'/{account}'`:

- **Every level is hardened**, so no public key your wallet publishes leads to it.
- **Purpose `1017'`** is one no on-chain wallet spends from (BIP44, BIP49 and BIP84 use other purposes), so the master seed can never be one of your wallet's spending keys.
- **Coin type `309'`** is CKB's.
- **The account** defaults to `0` and goes up to [`MAX_ACCOUNT_INDEX`](/docs/api/variables/MAX_ACCOUNT_INDEX) (2³¹ − 1). Each account is a separate tenant with separate channels, and a restore needs to know which accounts were used.

`deriveMasterSeed` is a pure function: it keeps nothing, and the SDK instance only ever holds the master seed, never the BIP39 seed above it. It accepts exactly 64 bytes ([`BIP39_SEED_LENGTH`](/docs/api/variables/BIP39_SEED_LENGTH)), which catches the easy mistake of passing the 32-byte master seed in twice. The constructor, in turn, accepts exactly 32.

:::warning[Use the same path forever]
You can derive the master seed some other way, but if your app ever changes how it does it, every channel opened under the old seed becomes unrecoverable. `deriveMasterSeed` exists so that the whole chain, from mnemonic to channel key, is fixed by the SDK.
:::

## What is derived from it

You never handle these keys: the SDK derives them when it needs them and never returns one. At a high level:

| Derived value | From | Used for |
| --- | --- | --- |
| **Wallet identity key** (the tenant's RootSigner) | The master seed | The key the LSP knows the wallet by. Its hash is the tenant id (`sdk.tenantId`, `deriveTenantId`) |
| **Channel seed** | The master seed and a **channel index** | The root of one channel's keys |
| **Funding key** | The channel seed | The device's half of the channel's 2-of-2 lock, and every musig2 signature |
| **TLC base key and per-commitment keys** | The channel seed | Settling pending payments and the device's balance after a force close |
| **Commitment secrets** | The channel seed | Revoking old channel states |
| **musig2 nonces** | The channel seed, a commitment number and the signing context | One deterministic nonce per signing slot |
| **Hold invoice preimage** | The master seed and an **invoice index** | Settling a payment the device receives |

Below the channel seed the scheme is Fiber's own, byte for byte, because the node derives the public halves of the same keys and builds transactions with them. The SDK's test suite checks every derivation against vectors generated by Fiber's Rust code.

Two indexes tie the tree to real channels and invoices, and both come from the device's clock: a channel's index is the time of its opening in seconds, an invoice's the time of its creation in milliseconds, each always above the last one handed out. That way a device whose storage was wiped can never hand out an index it already used, which would reuse nonces. The one thing that can break it is a clock set before the SDK's floor date, which the SDK refuses with the `clock_before_floor` error.

The wallet identity key depends on the master seed alone, not on the phone. Two installations restored from the same mnemonic are the same tenant to the LSP. That is what makes a restored wallet known again, and also why the LSP cannot tell two installations apart.

:::tip[The tenant id before the SDK]
[`deriveTenantId(masterSeed)`](/docs/api/functions/deriveTenantId) gives the same id as `sdk.tenantId` without building an instance, which is useful when you key your storage by tenant (see [Storage](/docs/concepts/storage#one-storage-per-master-seed)). It returns only the public id.
:::

## Deterministic on purpose

Fiber's own node draws each channel seed at random. The SDK derives it instead, and the trade-off is deliberate:

- **For**: the keys of every channel come back from the mnemonic and the channel's index. Losing the phone is not losing the keys.
- **Against**: all security rests on the master seed, and the derivation becomes a promise to every channel ever opened. Changing it would orphan them.

Nonces are deterministic too. That is what lets the device publish its nonce before it sees the message and answer a repeated request with the identical signature. It is only safe because the device never signs two different messages with one nonce, which is what [sign-once](/docs/concepts/no-blind-signing#sign-once) enforces.

## The scheme version

[`DERIVATION_SCHEME_VERSION`](/docs/api/variables/DERIVATION_SCHEME_VERSION) is the version of the whole derivation tree. Today it is `1`.

The scheme is **additive only**: a future version may add derivations for new channels, but version 1 keeps working forever, so channels opened today stay recoverable by any later SDK. If you keep backup metadata, it is worth recording the version next to it:

```ts title="backup.ts"
import { DERIVATION_SCHEME_VERSION } from "@peersyst/fiber-lsp-sdk";

// Store it next to your wallet's backup metadata, so a future restore knows which scheme made the keys.
const backupMetadata = { fiberDerivationScheme: DERIVATION_SCHEME_VERSION };
```

## What a restore does not bring back

The mnemonic restores keys. It does not restore the **signing state** the SDK keeps in your storage: which slots were signed, the versions of each channel's commitments, the values pinned at the opening, the payment budgets the user approved, the hold invoices and their indexes, and the list of channels the device opened.

After a reinstall with empty storage, the SDK knows no channel: it does not poll the old channels, and a signing request for one would be refused as `unknown_channel`. That is the safe side to fail on: it never signs under an empty sign-once registry, because a node could then get one slot signed again and again, and three signatures under one nonce reveal the funding key. What follows from it:

- **Open channels stall.** Nothing signs for them any more, and Fiber may force-close them (it does once a pending payment reaches its deadline).
- **A force close's funds wait.** After a force close, the watchtower's spend of the device's balance needs a signature from a device that holds the channel's record. Without it, the balance stays in the commitment cell, and the SDK has no way to sign that spend today.
- **A payment held on a hold invoice times out.** Releasing it needs the invoice's index, which was in storage, so the payment goes back to the payer.
- **A payment in flight is not reported.** The node still knows how it ended, but the SDK no longer watches it.

Rebuilding the signing state from the node is not something the SDK does today: everything the node reports is the node's word, and a record rebuilt from it is exactly what an attacker would want the device to trust.

:::danger[Never restore an older copy of the storage]
Empty storage is safe. *Older* storage is not: it reads slots the device already signed as free, so the node can get them signed again under the same nonces, which is how a funding key leaks. Keep the SDK's storage out of OS and cloud backups. [Storage](/docs/concepts/storage#never-older-than-it-was) explains the rule.
:::
